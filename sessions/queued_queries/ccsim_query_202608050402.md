## Diagnosis 1 (per `cp/ccsim/CLAUDE.md` §8.7)
- This reads as NOT-NOTICED, and a fairly clean case of it: CC's own reasoning, moments earlier in the same turn, explicitly restated the updated rule ("Emit that declaration in the SAME message as your next tool call") — the words were current, correct, and freshly re-read. The miss is that the model then generated a tool-calls-only message and the declare text simply never got typed, i.e. the failure sits at the boundary between "knowing what to do" and "the generation of the message actually doing it" — not a misreading of the instruction.
- This is a materially harder case than the sibling report's (stopping after a bare-text message): here nothing about the message's SHAPE was unusual — it had tool calls, which is exactly what the updated rule asked for. The declare text itself was just... absent. A structural nudge like "don't end on bare text" (the sibling report's proposed fix) would not have caught this, because the message didn't end on bare text — it never contained the required text anywhere.

## Diagnosis 2 (per `cp/ccsim/CLAUDE.md` §8.7)
- This reads as closer to MISAPPLIED than not-noticed, though genuinely mixed. CC had read the append-in-place rule at the start of the very same turn (it's part of the `#m2` snippet CC interprets before doing anything else) — the rule was not absent from context. But at the moment of actually drafting the answer sections, a DIFFERENT, competing organisational instinct won out without being reconciled against the rule: mirror the ORIGINAL QUERY's own section numbers (§5.2, §6.1, etc.) for easy cross-reference, rather than nest under CC's own plan point. That substitution happened silently — CC did not appear to weigh "nest under 11.4" against "mirror the query's §-numbers" and consciously pick the latter; it just defaulted to the second pattern, which is CC's much more common shape for numbered.md responses generally (mirroring a query's own structure is the default move in nearly every OTHER turn this session, `#m2` or not).
- Contributing factor worth naming: `m2.md`'s own worked example ("10 pts + 10 new = I read all 10 before learning they NO LONGER MATTER") illustrates the anti-pattern (redundant, superseding new pts) but does NOT show a worked example of the CORRECT shape for the common real case — a "thoughts/plan" point whose sub-points each promise a category of forthcoming answers, later fulfilled by MANY separate findings per sub-point. It's plausible the rule reads as obviously-clear in the abstract but under-specified for this exact shape, which would tip the diagnosis further towards not-noticed/under-specified rather than a clean misapplication.

## Candidate Fix Directions (for the receiving session to weigh, not decided here)
1. For Issue 1 (declare never emitted despite tool calls present): the sibling report's "don't end on bare text" fix doesn't cover this case. A stronger structural fix: make the interim declare part of a FIXED, checkable template CC must literally fill in and echo — e.g. require the exact string `➡️ **` to appear somewhere in the message before any tool call is permitted to close it out, enforceable in principle by a lightweight PostToolUse/PreToolUse hook that inspects the assistant's own emitted text for turns following an `#m2` response_ write, not just prose guidance.
2. For Issue 2 (flat new sections instead of nesting): add a short WORKED example to `m2.md` itself, showing a "thoughts" point with a multi-part sub-point (like 11.4's "(a)/(b)/(c)" list) and how its eventual answers should be nested (11.4.1/11.4.2/11.4.3...) rather than becoming new top-level points — concrete worked examples are what `numbered.md` itself already leans on elsewhere (§ Example List), and this rule currently only has an abstract anti-pattern, no worked correct shape.
3. Both issues share a root observation worth logging even if 1–2 aren't built: this was the SECOND `#m2`-adjacent miss in one session, on a file that had JUST been re-read specifically because it was freshly updated to fix the FIRST miss. That's some evidence the fixes so far (prose clarification) aren't fully closing this class of gap — worth weighing a structural/hook-based enforcement over a third prose iteration, per CCSIM's own §8.1 posture ("a rule that only works if someone recalls it at the right moment has already failed").
