# PDF→Markdown Conversion Needs a Standing Multi-Method Cross-Validation Default, Not a Reactive Re-Check

## Context (pointer only, NOT truth —— verify everything yourself)
- This session (career CP): `Culous - Part Time (Award) Employment Contract...pdf` was converted to `.md` by a sub-agent using the `Read` tool's page-range text extraction. The conversion dropped/misplaced an unnumbered "BACKGROUND" preamble section (1A/1B/1C) that sits between the contract's header block and its numbered clauses.
- User caught this by comparing against the source PDF himself; CC's fix (`sessions/2026/202608/career_response_202608050209.md` §11–§12) was to redispatch all 5 sibling conversions with a stricter brief: read the Read tool ONE PAGE AT A TIME (no ranges) and self-check for sequential clause numbering + explicit preamble/background presence.
- That redo genuinely worked: it fixed the BACKGROUND miss and caught a SECOND, previously-unknown gap in a sibling file (Employee Handbook §16 Grievance, a dropped clause fragment) as a side effect of the more careful pass.

## What Happened, and Why It's Still a Gap
- Despite the redo's success, the verification brief CC wrote for it — and CC's OWN personal spot-check afterwards — was framed around confirming/denying the ONE known symptom ("does BACKGROUND appear correctly, yes/no") rather than a generic, method-independent completeness check. The user's own words, next turn: "you sounded like you were just hunting for the BACKGROUND section from each file, which it was just one example of miss-out."
- The underlying issue: the redo still used the SAME extraction method as the original pass that missed content (the Read tool's PDF text-layer extraction), just applied more carefully (page-by-page instead of ranged). Careful re-application of the same method can catch SOME classes of miss (content lost at a range boundary) but not others (anything the text layer itself doesn't faithfully represent — reading-order issues, text boxes, stamps, unusual layout) — a single-method check, however careful, has a structural blind spot to its own method's failure modes.
- The user's own proposed fix, verbatim: "all future PDF parsing/conversion must use multiple means to cross-validate, w/ OCR used at least to see exactly what humans see" — i.e. an independent SECOND method (rendering pages as images and visually reading them, closer to what a human proofreading the physical/scanned document would do) should be a STANDING part of converting any legal/important PDF, not a reactive step taken only after a miss is already known and confirmed.

## Why This Is Worth Fixing as a Default, Not Just This Session's Judgement Call
- The failure mode here is not "CC didn't try hard enough once told" — CC DID respond thoroughly once the miss was flagged (this session's redo + a further dispatched visual/image-rendered cross-check, per the user's follow-up query, are both genuine, careful responses). The gap is that the FIRST pass, and the verification framing immediately after a known miss, both defaulted to a single method (careful text extraction) as if thoroughness-within-one-method were equivalent to cross-validation across methods. That default is the thing worth changing, not any one session's effort level.
- Per `cp/ccsim/CLAUDE.md` §8.1 ("prefer a lint, hook, or default that makes the wrong move hard over an instruction that asks for the right one") and §8.7 (a not-noticed gap is an enforcement gap, and restating the rule in prose doesn't close it) — this is a good candidate for a standing default rather than relying on CC to remember "be extra careful" every time a legal/important PDF is converted.

## Candidate Fix Directions (for the receiving session to weigh, not decided here)
1. A protocol addition (likely in `universal/coding.md` or a new small `universal/pdf.md`, or a note in `cic.md`'s neighbourhood) stating: any PDF→Markdown conversion of a LEGAL or otherwise high-stakes document (contracts, statutory statements, anything where a miss has real-world consequences) MUST use at least 2 independent extraction methods and cross-validate between them before being treated as complete — e.g. (a) the Read tool's page-by-page text extraction, AND (b) a visual/image-rendered read of each page (via `pdftoppm`/`sips`/a Python PDF-to-image library, then the Read tool on the resulting images) — not sequentially-applied care within one method.
2. Bake this into the SA-briefing habit itself: when root CLAUDE.md's §9.02 SA-dispatch guidance is invoked for a document-conversion task, the brief should default to requesting BOTH methods up front, rather than starting with one method and only escalating to a second after a human catches a miss. This turns "cross-validate" from an escalation response into the first-pass default.
3. If a lint/hook is feasible: a lightweight advisory (like `plint`) that fires when a `Write`/`Edit` targets a path matching `*/MD/*.md` or similar "converted document" shape, reminding whichever agent is about to finalise it to confirm a second, independent method was used — cheap, non-blocking, keeps the judgement call with CC/the SA rather than hard-gating.
4. Lower-cost partial fix, if 1–3 aren't built: at minimum, record this as a standing note somewhere CC re-reads before ANY future document-conversion task (not just Alltech), since the current gap is that carefulness-within-one-method was mistaken for completeness, and that mistake is easy to repeat on the next legal-document conversion task in an entirely different CP.
