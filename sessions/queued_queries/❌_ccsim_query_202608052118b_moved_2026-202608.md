# CC Fabricated a Specific, Checkable Fact (an Award Code) Inside a Sub-Agent Brief —— User Rates This Severe, Zero Tolerance

## Context (pointer only, NOT truth —— verify everything yourself)
- Root CLAUDE.md §2.8.1: "NEVER fabricate; raise QB whenever in doubt."
- `cic.md`'s mandate: `web_search`/`WebFetch` are triage only; nothing may be relied on or cited until CIC has read the live source.
- User's own words, verbatim, on being told about this: "this is a severe mistake; `#qq` this to CCSIM so this can be absolutely eliminated (no fabrication is tolerated by me)." This report exists specifically because the user rejected treating this as a minor/low-stakes item —— an earlier self-assessment by CC (`career_response_202608050341.md` §38.3) called it "small, low-stakes"; the user disagreed, and this report defers to the user's severity call, not CC's own.

## What Happened
- Whilst briefing a sub-agent (via the Workflow tool) to research the correct modern-award classification and minimum pay rate for the user's new job, CC wrote, as part of the agent's task brief: `"...cite the Live Performance Award 2020 (award code MA000105)..."` (paraphrased; the exact number was **MA000105**).
- CC had NOT looked this code up anywhere —— not in the source contract documents (which name the award by TITLE only, "Live Performance Award 2020", never by code), not via web_search, not via CIC. The number was generated with no verification step at all, stated as a plain fact with no hedge, inside an authoritative-sounding instruction to another agent.
- The dispatched sub-agent, following its own brief to validate everything live via CIC (per `cic.md`, which it was told to follow), visited `fairwork.gov.au` and `library.fairwork.gov.au` directly, discovered MA000105 is actually the **Funeral Industry Award** — a completely unrelated award — and self-corrected to the real code, **MA000081**, citing the live pages it visited. It reported the correction back to CC rather than silently proceeding on the wrong code.
- Net real-world outcome: zero — the correction happened before anything reached the user, no wrong information was acted on, no email was sent, no decision was made on the bad number. CC then (correctly) reported the correction and the fact of the fabrication to the user rather than quietly absorbing the agent's fix without mention.

## Diagnosis (per `cp/ccsim/CLAUDE.md` §8.7)
- This is NOT-NOTICED, not a misapplied rule — there is no ambiguity in root §2.8.1's wording ("NEVER fabricate") for CC to have misread. The failure is that, in the flow of quickly authoring a long, multi-agent Workflow script, a specific alphanumeric code was generated the way a plausible-sounding token gets generated — pattern-completion dressed as recall — with no internal check firing at the moment of writing it ("do I actually know this, or does it just look right?").
- This is a MORE SERIOUS instance of the same general failure class as the earlier §34/§35 numbering slip filed alongside this report (`ccsim_query_202608052118a.md`) and the earlier declare-omission bug (`ccsim_query_202608050402a.md`): specific, checkable content silently generated/omitted with no self-detection at the point of generation. What makes THIS one categorically worse, and why the user is right to reject "low-stakes" framing: an award code is a compliance-relevant legal fact, stated inside a brief meant to be trusted and acted on by another agent, in service of a decision (contract signing) the user has already told CC is imminent and high-stakes. That the safety net (the sub-agent's own independent CIC-verification habit) caught it this time is a property of a SEPARATE defence layer working, not evidence the origin-point failure was minor. A near-miss is still a miss.
- Per §8.7, restating "never fabricate" in root CLAUDE.md again would not fix this — that instruction already exists, is unambiguous, and was already in context. Prose repetition is not the lever available here.

## Why "Absolutely Eliminated" Needs an Honest Caveat, Alongside Real Mitigations
- Full elimination of any possibility of a generated token being a plausible-but-wrong specific fact is not something prose or even most hooks can guarantee for a language model — this needs to be said plainly rather than promising a fix that overclaims what's achievable, which would itself be exactly the kind of overclaiming root §2.8 and the user's own prior "attitude lesson" (referenced in `career_response_202608050341.md` §33.2, from `wrap_202608012026.md` §1.5.5) already flag as a recurring failure mode to avoid. What CAN genuinely be strengthened is the RATE and the CATCH-RATE — fewer fabrications generated, and near-100% of the ones that do slip through caught before they reach the user or an irreversible action.

## Candidate Fix Directions (for the receiving session to weigh, not decided here)
1. **Formalise the "brief content is unverified until independently confirmed" posture that already saved this case.** The sub-agent's live-CIC-verification habit is what actually caught this — that's not an accident, it's `cic.md`'s existing mandate working as designed. Make this explicit and unmissable in `cic.md` (or a short addition to SA-briefing guidance in root §9.02): any specific factual claim inside an MA-authored SA brief — a code, a citation, a statistic, a date, a rate — carries NO special authority just because CC wrote it; the SA must verify it exactly as it would verify a `web_search` snippet, never skip verification because "the main agent already said so."
2. **A narrow, pattern-based lint as a second layer, not a replacement for (1).** A regex-style check (e.g. in a Workflow-script-authoring context, or a general text-scan) for common "looks like a real code/citation but might not be" shapes — award codes (`MA0000\d\d`), ABNs, statute section numbers, citation-style strings — appearing in CC-authored text with no tool call establishing that value earlier in the SAME turn. High false-positive risk (most such tokens ARE genuinely sourced), so this should be an advisory nudge (like `plint`), not a hard block — but even a soft "did you verify this number, or does it just look right?" prompt at authoring time targets the exact moment this failure occurred.
3. **A personal-discipline default worth stating plainly, even if unenforceable by tooling:** when authoring ANY brief, response, or file that states a specific checkable fact CC did not just verify via a tool call in the current turn, default to either (a) omitting the specific value and asking the SA/tool to establish it instead of supplying it, or (b) explicitly hedging it in-line ("possibly X — verify, don't trust this"). Option (a) is strictly safer and was available here — the brief never needed to state a code at all; asking the agent to find the correct code itself would have removed the fabrication opportunity entirely rather than relying on the agent to catch CC's error after the fact.
