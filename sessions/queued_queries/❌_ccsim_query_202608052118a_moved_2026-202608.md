# Edit-Tool Section Insertion Silently Dropped a Heading, Orphaning Its Sub-Points Under the Wrong Number

## Context (pointer only, NOT truth —— verify everything yourself)
- Found in `sessions/2026/202608/career_response_202608050341.md` (now fixed in place, see below) —— flagged by the user: "your heading is 34 but the pts are 35.1, 35.2, etc." then `#qq`'d to CCSIM.
- Mechanism, reconstructed precisely from the edit history: an `Edit` tool call needed to insert two NEW sections (33, 34) immediately before an EXISTING section whose heading was `## 35. Re 18.4 —— Disentangling "Floor" from "Mildly Cautious"`. The `old_string` matched ONLY that heading line (a common, minimal-diff pattern —— match the shortest unique anchor, here the heading, to insert content just before it). The `new_string` supplied `## 33. ...` and `## 34. Re 18.3 —— Answered at §37.3` but did NOT re-include the original `## 35.` heading line at the end of the replacement. Since `Edit` only touches the matched span, the untouched body content that followed in the file (`- 35.1. ...` through `- 35.4. ...`) stayed exactly where it was —— now sitting directly under `## 34.` with no `## 35.` heading above it at all.

## Diagnosis (per `cp/ccsim/CLAUDE.md` §8.7)
- Cleanly NOT-NOTICED, and unusually mechanical as these things go: there was no rule to misread here, no protocol ambiguity, no competing instinct. The content itself was entirely correct (section 35's own sub-points were fine); the heading that should have re-appeared simply wasn't retyped, and nothing in the moment surfaced that omission back to CC. This is closer to a copy-paste/typo class of error than a judgement or comprehension failure —— which points towards a MECHANICAL detection fix over a prose one, per §8.7's own steer ("only a misapplied rule is fixed by rewriting the words").

## Why This Is Worth a Standing Check, Not a One-Off Fix
- The failure SHAPE is generic and will recur: any time `Edit` is used to insert new numbered section(s) immediately before an existing heading by matching only that heading line, the same silent-drop is possible if the replacement forgets to re-terminate with the original heading. This isn't specific to this response_, this CP, or `#m1`/`#m2` —— it's a property of how `numbered.md`-style responses get incrementally built up via targeted `Edit` calls across a long turn, which is now this session's default working pattern for every multi-section response.
- The defect is EXACTLY the shape `nlint` already exists to catch (per `cscpt/README.md`/the nlint hook seen firing elsewhere this session on `AlltechAV_MarketingGrowthCoordinator...md`'s pre-existing §5.1 overflow) —— it's a numbering-structure check, not a content-judgement one, and numbering-structure checks are nlint's whole job.

## Candidate Fix Directions (for the receiving session to weigh, not decided here)
1. Extend `nlint` with a heading/body-number CONSISTENCY check: for every `## N.` (or `## N. [Title]`) heading, the FIRST numbered bullet that follows (before the next `## ` heading) should begin `N.1`. If it instead begins `M.1` for some `M ≠ N`, flag it —— this is a simple, deterministic, whole-file scan (heading number vs. first child bullet number) that would have caught this exact bug the moment the file was next linted, rather than requiring the user to notice it by eye.
2. This check is orthogonal to, and can sit alongside, the existing "9⁺ items on a level" nlint check already in place —— same tool, same class of structural scan, just a different specific pattern.
3. If a full nlint rule isn't wanted, a lighter version: have the existing quick-dlint hook (which already re-scans the whole file on every `Write`/`Edit`, per this session's observed behaviour) run this same heading/body-number check as part of its pass, since it's already touching every edited comms file anyway.
