# Root CLAUDE.md §6.2 Is Missing the "CP Only Ever Added, Never Switched" Invariant — CC Propagated a User's Filing Typo Instead of Self-Correcting It

## Context (pointer only, NOT truth —— verify everything yourself)
- Root CLAUDE.md §6.2: "Identify as a CP session when any of the following applies: 6.2.1. The query_ file is [CP_folder]-prefixed... 6.2.2. User declares it... 6.2.3. User added CP as working dir." §6.3.2 covers the OPPOSITE direction only: "If any files since (not just after) query_ triggering CP not prefixed: rename → declare" — i.e. what to do when files SHOULD have a CP prefix and don't. Nothing in §6 currently addresses a query_ arriving with a prefix that CONFLICTS with the session's already-established CP.
- What happened: this session identified as `career` CP from its first query (turn 2, `career_query_202608041846.md`) and stayed `career`-prefixed for turns 2`~`4. Turn 5's query arrived filed as `ccsim_query_202608052112.md` — despite its own body text opening "# Reply to career_response_202608050341.md" and being substantively a continuation of the same Alltech/career thread. CC noticed the mismatch, reasoned about it at length (considered "maybe a naming mistake," considered "maybe intentional"), could not resolve it confidently from the written protocol, and defaulted to following the literal filename prefix — filing its own response as `ccsim_response_202608052112.md` too, whilst flagging the ambiguity in-file for the user to correct.
- The user's own words, next turn: "my fault; and i fixed both my query and my response to set the record right, both `career_` prefixed now... i would NEVER change CP midway, only ADD CP; i.e. if ses is non-CP, i might make it a CP ses; if ses is already a CP ses, i will never change it; any comms file prefix change MUST be user error and CC should fix it and stop it from further worsening."

## Diagnosis
- This is a genuine WRITTEN-PROTOCOL GAP, not a not-noticed slip or a misapplied rule —— CC's own reasoning at the time explicitly considered the possibility that the mismatched prefix was a user typo, but had no stated invariant in root CLAUDE.md to confidently act on that suspicion, so it hedged (followed the literal filename, flagged the ambiguity) rather than self-correcting. Per `cp/ccsim/CLAUDE.md` §8.7's own taxonomy, this sits outside NOT-NOTICED/MISAPPLIED entirely: the rule the user now wants enforced simply did not exist in writing yet. This is the rare case where WRITING NEW WORDS is squarely the right fix (unlike the session's other CCSIM reports, where restating an existing rule was diagnosed as insufficient) — because the gap is that the rule was never stated, not that it was stated and missed.
- Secondary cost worth naming: by hedging instead of self-correcting, CC also PROPAGATED the user's typo one step further (creating a `ccsim_response_` file that then also needed manual renaming), rather than containing it. The user's phrase "stop it from further worsening" is precise —— the current protocol has no mechanism telling CC to be the CONTAINMENT point for this exact class of error.

## The Invariant to Add (user's own formulation, ready to adapt)
- A session's CP identity, once established (via any of §6.2.1`~`6.2.3), is monotonic: it can go from NO CP → a CP, but never from CP=X → CP=Y within the same session.
- Therefore: any query_ file arriving with a DIFFERENT CP prefix than the session's already-established CP is, by definition, a user filing error (typo, habit slip from a recently-used prefix, copy-paste artifact) — never a genuine mid-session CP change.
- On detecting this: CC should (a) rename the query_ file back to the session's established CP prefix (per the existing Move Rule machinery, §8.1, since this is functionally a rename-for-correctness action), (b) keep its OWN response_ under the established CP throughout — never let the mis-prefixed query propagate into CC's own output, (c) briefly declare the correction made (a new case for the existing declaration system, not a silent fix, so the user sees it happened), rather than flagging the ambiguity and asking/hedging as happened this time.
