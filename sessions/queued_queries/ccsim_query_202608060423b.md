# hlint Fired `#wrap`/`#numbered` False-Positives on a Task-Notification Turn With No User Text at All

## Context (pointer only, NOT truth —— verify everything yourself; CC does not have hlint's source and is reconstructing from observed behaviour only)
- hlint is described (via its own repeated non-blocking reminders throughout this session) as a "UserPromptSubmit hook" that scans for hashtag-trigger patterns and fires reminders like `` `#X` detected —— READ `universal/X.md` ``.
- Root CLAUDE.md §7.3.3: "Alert w/ ⚠️ if trigger unrecognised or file not found" — this session did NOT do that for `#wrap`/`#numbered`, because they ARE recognised, real triggers (`universal/wrap.md`, `universal/numbered.md` both genuinely exist) — the problem isn't an unknown trigger, it's the trigger firing on a turn where NO user text existed for it to have matched against.

- Sequence of events in this exact order, one continuous turn boundary:
  1. CC dispatched a Workflow (`w19qyjk6n`, "Convert 2 new Alltech docs (dual-method), verify+diff onboarding plan lineage, and CIC-research Address/DOB norms, FOF") and the turn ended (CC made a legitimate tool-call-based pause whilst the background fleet ran, per this session's established pattern for waiting on long-running work).
  2. The NEXT content CC received was a `<task-notification>` block —— explicitly marked, in the notification's own boilerplate text, as: "This is an automated background-task event, NOT a message from the user... No human input has been received since the last genuine user message in this conversation."
  3. Immediately following that task-notification, in the SAME turn, a `[hlint hook] Possible hashtag-trigger(s) detected` reminder appeared, flagging `#wrap` and `#numbered` as "detected" and instructing CC to read `universal/wrap.md`/`universal/numbered.md`, framed exactly as it frames a genuine hashtag typed by the user elsewhere in this session.

## Diagnosis —— Hypotheses, Ranked, With Honesty About What CC Cannot Verify
CC has no access to hlint's implementation and cannot definitively identify the mechanism. The following are ranked by plausibility given the observed evidence, offered so CCSIM can verify against the actual source rather than CC guessing further:

1. **Most plausible: hlint's scan scope isn't restricted to genuine user-authored prompt text.** If the hook is wired to fire on "the next inbound message" generically (rather than specifically on a message the harness has tagged as user-authored), a task-notification's JSON payload — which in this case embedded several very large sub-agent report strings (one agent report ran to ~16,000+ characters, itself containing nested quotes, markdown, and arbitrary prose from an LLM sub-agent describing document contents) — becomes fair game for a naive substring/regex hashtag scanner. A large enough block of LLM-generated prose discussing document structure, headings, formatting conventions etc. has a non-trivial chance of coincidentally containing patterns a hashtag-regex would match (e.g. markdown `####` heading marks, a literal mention of "numbered list" near an unrelated `#`, a URL fragment).
2. **Plausible: the hook fires on a fixed cadence/every-turn basis rather than being gated on "was this a genuine UserPromptSubmit event", and mislabels itself.** I.e. despite being NAMED a "UserPromptSubmit hook", it may actually be implemented to run on every new inbound harness event regardless of type, with the "UserPromptSubmit" label being aspirational/historical rather than an enforced gate.
3. **Less plausible but worth ruling out: a stale/cached scan target.** If the hook scans "the most recent user message" by some indexing/lookup that isn't correctly invalidated between a real user turn and an intervening notification-only turn, it could be re-scanning OLDER content from a genuinely earlier point in the session (though neither `#wrap` nor `#numbered` as literal typed hashtags appear to have been part of this session's actual query_ files either, based on what CC can recall — worth CCSIM independently grepping all this session's `query_` files for both strings to fully rule this out, since CC's own memory of its context is not authoritative).
- Per `cp/ccsim/CLAUDE.md` §8.7's framework applied to hlint's OWN behaviour (not CC's): this is a tooling/enforcement-mechanism bug, not a CC comprehension failure — CC handled the false trigger correctly once it fired (declared, didn't act, deferred to the user). The thing that needs fixing is upstream of CC's own reasoning entirely.

## Why This Matters Beyond Being a Minor Annoyance
- hlint's entire value proposition is that its reminders can be trusted enough to act on without independently re-verifying each one — root CLAUDE.md §7.3.1`~`2 treats a hashtag detection as something CC "MUST" read the corresponding protocol file for. A hook that can fire on content the user never typed erodes that trust and forces CC (or the user) to second-guess every future firing — exactly the kind of "is this real or noise" burden the whole hlint/dlint/nlint/plint suite exists to remove per CCSIM's own Operating Posture (§8.1).
- It also creates a specific NEW risk: if a future false-positive happens to name a trigger whose protocol file, once read, changes CC's behaviour in a way that's hard to reverse or costly to have acted on unnecessarily (unlike `#wrap`/`#numbered`, which were low-cost to just declare-and-skip), a less careful pass could act on a phantom instruction.
