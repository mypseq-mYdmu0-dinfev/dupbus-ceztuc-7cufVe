## 12. Verified —— A1 (Remote-Control)
- 12.1. "Need `/remote-control` run 1st" —— confirmed as default; an "Enable Remote Control for all sessions" (auto-connect) toggle exists (`/config`, Desktop Settings, or `remoteControlAtStartup`) that removes the manual step for NEW sessions
- 12.2. Disconnect on app restart —— confirmed BY DESIGN ("local process must keep running"; closing the CC process/app ends the ses) —— an architectural limit, not a bug
- 12.3. Disconnect on fork —— not explicitly documented, but medium-confidence inference: `/fork` creates a brand-new ses ID w/ no recorded remote-control pairing —— would need auto-connect ON to self-heal
- 12.4. Disconnect on revert —— unconfirmed either way; genuine research gap, not a contradiction
- 12.5. Haiku prohibition —— NOT supported by docs; likely a misconception. Real (unrelated) restriction: "Auto" permission mode is unavailable over remote-control for ANY model, not Haiku-specific
- 12.6. Mass simultaneous disconnects —— phenomenon confirmed real & currently OPEN (issue #80311: exponential-backoff teardown killed 14 sessions across `~`2 days); but "Anthropic-side deploy" as the cause is unconfirmed —— documented trigger is a client-side transient network blip, not an acknowledged server deploy
- 12.7. The auto-connect toggle itself is reported unreliable specifically on the Desktop app across multiple open issues —— no fully reliable persistent-pairing exists today

## 13. Verified —— A4 (Dispatch)
- 13.1. Structural correction: Dispatch is NOT a separate stateless tab —— Anthropic's docs describe it as "a persistent conversation... that lives in the Cowork tab"; ONE continuous thread, context retained across tasks, BY DESIGN
- 13.2. This directly contradicts your "no continuity between queries" —— what you actually experienced matches a severe, real, currently-OPEN reliability bug (issue #40179: msgs marked "Read", zero response, many independent users over months)
- 13.3. Practical tip surfaced: a "silent" dispatch sometimes DID complete —— check the Dispatch dropdown → "See background tasks" before assuming total failure
- 13.4. Separately (issue #37713): a fresh Dispatch task spawns in an isolated sandbox w/ NO access to the parent Project's folder/`CLAUDE.md` —— so even once reliability improves, it may not auto-inherit repo context
- 13.5. Requires Pro/Max (not Team/Enterprise); app permissions in Dispatch-spawned sessions expire after 30min

## 14. Verified —— A5 (Cowork)
- 14.1. Directory/repo scoping —— confirmed via 2 mechanisms: "Projects" (link a local folder as Context + separate Instructions + Memory —— closest built-in `CLAUDE.md` analogue) or a lighter ad hoc "folder instructions"
- 14.2. Literal `CLAUDE.md` auto-load —— NOT confirmed either way; manually asking Cowork to read a specific `CLAUDE.md` should work as a plain file-read (file I/O confirmed), but that's inference, not documented behaviour
- 14.3. Capability —— file r/w (scoped to connected folder), computer-use/app-running (Pro/Max, OFF by default, needs a Desktop toggle), and browser control ARE all confirmed, incl. driving Claude in Chrome itself
- 14.4. Important nuance: Cowork sessions run in the CLOUD by default (Anthropic's sandbox), bridging to your Mac's Desktop app only for local resources —— NOT literally executing on WSM the way a CC terminal ses does. An older "local execution" mode exists for "existing desktop deployments" —— worth checking your Settings to see if that applies to you
- 14.5. Rollout: Pro-tier web/mobile access is still gradually rolling out per the docs' own wording ("over the next several weeks") —— may explain why your 1 test felt thin
