# Response to query_202607092019.md
*Malformed Word `open` Call —— Fixed*

1. Root cause found in `PDF Conversion.app/Contents/document.wflow`'s Full-Mode Word branch:
- 1.1. It read `set theDoc to open file name (theFile as text)` —— but Word's AppleScript `open` command has NO `file name` parameter (that label only exists on `save as`). AppleScript couldn't parse it as a command argument, so it fell back to reading it as a property reference —— "the `file name` OF `(theFile as text)`" —— and since a plain text string has no such property, Word threw exactly the error you saw: "The object you are trying to access does not exist."
- 1.2. Confirmed by comparison: the sibling Excel branch (`open (theFile as text)`) and PowerPoint branch (`open theFile`) both omit `file name` entirely —— only Word's had it, a copy-paste-style inconsistency unique to that one branch.

2. Fix applied: Word branch now matches its siblings' proven pattern —— `open theFile` (no bad label), then fetch the doc via `active document` (mirroring Excel's `active workbook` / PowerPoint's `active presentation`) instead of relying on `open`'s return value.

3. Secondary issue also fixed (same failure mode, same root cause class): NONE of the 3 native-app (Full Mode) branches were wrapped in `try`/`end try`, unlike the Quick-Mode LibreOffice branch which is. That's WHY the run left an empty `202607092018/` folder behind —— the unhandled Word error aborted the whole script mid-loop, skipping the end-of-run cleanup logic that deletes an empty output folder. All 3 branches (Word/Excel/PowerPoint) are now `try`-wrapped, so a single file's native-conversion failure no longer kills the batch or skips cleanup —— it just leaves that one file unconverted (originals are only ever deleted on confirmed success, so nothing was ever at risk).

4. Verified: `plutil -lint` confirms the edited `document.wflow` is still valid XML/plist.

5. Cleanup: your 6 originals were correctly left untouched by the crash (as designed —— delete only happens after confirmed success); the empty `❌_202607092018/` is voided for your manual delete. `202607092014/` (the earlier successful Quick-Mode run, 6 PDFs) is untouched and unrelated to this bug.
